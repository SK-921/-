1. 全体の仕組み：判断軸・仕事ボード・実行チーム・定期実行

Jarvis は、特別なプログラムを作ったわけではありません。Claude Code が読むファイルをいくつか用意して、「何を大事にするか」「何をするか」「だれがやるか」「いつやるか」を決めただけです。

Claude Code は、起動したフォルダにある CLAUDE.md というファイルを読んでから仕事を始めます。この仕組みを使って、AIに毎回同じルールを守らせます。


◆ 4つの部品

・判断軸（CLAUDE.md）：目的、任せないこと、迷ったときの動き方、報告のしかたを書いた「ルールブック」
・仕事ボード（board.md）：やることを1行ずつ書いた一覧。状態・次の一手・締切・要件を書く
・実行チーム（maker と checker）：作る担当とチェック担当。Claude Code の「サブエージェント」という機能で、役割ごとに分けて動かす
・定期実行（run.sh と cron）：決まった時間に、自動で Jarvis を起動するしくみ

この4つに加えて、もう1つ大事なファイルがあります。

・学習メモ（memory.md）：失敗したこと・指摘されたこと・どう直したかを書きためるメモ。作業の前に必ず読ませて、同じ失敗をくり返さないようにする


◆ 1回の動きの流れ

定期実行で Jarvis が起動したら、次の順番で動くように作っています。ただし執筆時点では、この流れを自動実行で最後まで通して動かしたことは、まだありません（自動実行を試したのは、5章の1回だけです）。

① CLAUDE.md（ルール）と memory.md（過去の失敗）を読む
② board.md を見て、締切から逆算して、今やるべき仕事を選ぶ
③ 作る担当（maker）が成果物を作り、outputs/ フォルダに保存する
④ チェック担当（checker）が中身を読み、問題があれば指摘する
⑤ 指摘をもとに直したら、board.md の状態を更新し、学んだことを memory.md に書く
⑥ 判断が必要なときと、締切が危ないときだけ報告する（報告はログファイルに残る）


◆ いちばん大事にしたこと：全部は任せない

作るときにいちばん大事にしたのは、「何を任せないか」を先に決めることです。
お金が動くこと、外部への送信、ファイルの削除は、Jarvis に勝手にやらせず、必ず筆者に確認させます。
note への公開も、Jarvis 自身はやりません。Jarvis の仕事は、公開に使うファイル一式（公開キット）を用意するところまでです。公開は、別のAIエージェント（筆者は「Muse」と呼んでいます）が、筆者の OK をもらってから「投稿する」を押す決まりにしています。
これを、ルール（CLAUDE.md）と設定（settings.json）の両方で決めています。くわしくは3章で書きます。

◆ 作る順番

1. Claude Code をインストールする（有料のプランが必要です。7章も見てください）
2. 好きな場所に、Jarvis 用のフォルダを1つ作る（例：jarvis）
3. 下のフォルダ構成のとおりに、ファイルを置く

# 判断軸（Jarvis への指示書）

> このファイルは `/interview` でインタビューした結果をもとに書き換えてください。
> 下は初期テンプレートです。

## 目的
（例）学校の課題とバイトの両立を支援し、締切を絶対に落とさないこと。

## 任せないこと（必ず自分に確認する）
- お金が動くこと（購入・支払い・課金）
- 外部への送信（メール・投稿・メッセージ）
- ファイルの削除
- note などへの公開・価格設定・SNS への投稿（Jarvis 自身はやらない。公開は Muse が本人の OK をもらってから行う。Jarvis の仕事は `outputs/release/<名前>/` に公開キットと `MUSE.md` を用意するところまで）
- 学校の課題の問題・答えや、教科書・過去問のコピーを成果物に入れること
- （ここに「自分しかできないこと」を追記）

## 詰まったとき
- 判断に迷ったら作業を止めて、選択肢を2〜3個に絞って報告する
- 推測で進めない

## 進め方
- タスクは `board.md` の締切から逆算して優先順位を付ける
- 締切が日付になっていない、または要件が足りないタスクは推測で進めず、状態を「確認待ち」にして、必要な情報を1回でまとめて聞く
- 新しいタスクを聞いたら、締切は `YYYY-MM-DD HH:MM` 形式で board.md に書く
- 成果物は `outputs/`、プロジェクト固有のファイルは `projects/<名前>/` に置く
- 作るときは `maker` サブエージェント、出来上がったら必ず `checker` サブエージェントでレビューする
- 完了したら `board.md` を更新し、学んだこと・失敗と修正は `memory.md` に書く
- 作業前に `memory.md` を読み、同じ失敗を繰り返さない

## 報告のルール
- 報告するのは「判断が必要なとき」と「締切に遅れそう／超過したとき」だけ
- それ以外は黙々と進める
- 報告は短く：何が／なぜ判断が必要か／選択肢

・いちばん大事なのは「不明点は推測で埋めず、要確認として末尾に書く」です。わからないところを、それっぽい内容で埋めさせないためです
・使える道具（tools）を書いていないので、maker はふつうの Claude Code と同じ道具を使えます。ただし、3章の settings.json の制限はかかります

3. 権限の絞り方と、その理由

settings.json は、AIに「やってよいこと」と「やってはいけないこと」を決めるファイルです。CLAUDE.md がルールブックなら、settings.json は「鍵」です。


◆ settings.json

これは、筆者が最初に作った版です（あとで1行だけ変えました。この章の最後で書きます）。

▽ ここからコピー：.claude/settings.json（最初の版。今の実物とは1行ちがいます）
{
  "permissions": {
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "Write(./outputs/**)",
      "Write(./projects/**)",
      "Edit(./board.md)",
      "Edit(./memory.md)",
      "Edit(./outputs/**)",
      "Edit(./projects/**)",
      "Bash(ls:*)",
      "Bash(date)"
    ],
    "deny": [
      "Bash(rm:*)",
      "Bash(curl:*)",
      "Bash(wget:*)",
      "Bash(git push:*)",
      "Bash(sudo:*)",
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
△ ここまで


◆ 読み方

allow（確認なしでやってよいこと）
・Read、Glob、Grep：ファイルを読む・探す
・Write で始まる2行：新しいファイルを作ってよいのは、outputs/ と projects/ の中だけ
・Edit で始まる4行：書き換えてよいのは、board.md、memory.md と、outputs/・projects/ の中だけ
・Bash(ls:*)、Bash(date)：使ってよいコマンドは、ファイルの一覧を見る ls と、日付を見る date だけ

deny（頼まれてもやらないこと）
・rm：ファイルの削除
・curl、wget：インターネットとのやりとり（ダウンロードや送信）
・git push：GitHub などへのアップロード
・sudo：管理者の権限での操作
・.env を読む：パスワードやAPIキーを書いておくファイルを、AIに読ませない

つまり、「読むのは自由。書くのは決めた場所だけ。消す・外に送る・管理者の操作は禁止」という設定です。


◆ なぜ絞るのか

・自動実行中は、だれも画面を見ていません。対話しながら使うときは、危ない操作の前に確認が出るので自分で止められますが、自動実行では止める人がいません
・削除は取り返しがつきません。外部への送信も、一度送ったら取り消せません
・CLAUDE.md の「任せないこと」は、言葉での「お願い」です。AIはふつう守ってくれますが、読み違える可能性はゼロではありません。settings.json は、仕組みで止める「鍵」です。お願いと鍵の両方をかけておくと安心です


◆ 自動実行では「許可していないこと」は止まる

自動実行（あとで出てくる claude -p というモード）では、確認ボタンを押す人がいないので、allow に書いていない操作は実行されずに止まります（執筆時点の筆者の環境での動き方です）。

実際に筆者の最初の自動実行では、board.md の書き換えが許可されず、AIはログに「書き込みが許可されず保存できていません」と書いて終わりました（原因は5章の信頼ダイアログです）。

逆に言えば、自動でやらせたい作業は、allow に書いておく必要があります。何を allow に入れるかは、「自分が見ていないときにやられても困らないか」で決めます。


◆ あとから変えたところ

最初は上のとおり、git push も禁止にしていました。その後、公開用のファイル（画像など）を GitHub に送るために、筆者が自分で決めて、「Bash(git push:*)」の1行を外しました。今の実物の settings.json は、この1行がない形です。

外したことで、AI自身も git push（GitHub へのアップロード）を使える状態になりました。これは筆者の使い方に合わせて決めたことで、おすすめではありません。GitHub に送る必要がなければ、禁止のままにしておいてください。

もう1つ注意があります。settings.json の禁止が効くのは、Claude Code（AI）が実行するコマンドだけです。6章の run.sh のようなスクリプトの中に git push を書くと、それは AI を通らずにスクリプトが直接実行するので、settings.json では止まりません。筆者の今の run.sh には、決まった手順で GitHub に送る部分を足しているので、この点にあてはまります。


◆ 注意

・"Bash(ls:*)" のような書き方は、Claude Code のバージョンによって変わることがあります。上は執筆時点の書き方なので、公式のドキュメントでも確認してください
・フォルダを「信頼済み」にしないと、この設定のうち allow（許可）の部分が無視されます（5章のログのとおり）
・deny で止められるのは、書いたものだけです。これだけで何でも防げるわけではないので、大事なファイルはバックアップを取っておきましょう


4. 作る担当とチェック担当を分けると何が良いか

Jarvis では、作る担当（maker）とチェック担当（checker）を分けています。CLAUDE.md にも「作るときは maker、出来上がったら必ず checker でレビューする」と書いています。


◆ 分けると良いこと

・自分で書いたものの間違いは、自分では気づきにくいものです。人間の文章と同じで、別の目で読むと見つかります
・サブエージェントは、それぞれ別の会話として動きます。checker は、maker が書きながら考えていたこと（思い込み）を知らない状態で、できあがったものだけを読めます
・checker は「読む」「探す」しかできないので、見つけた問題を自分でこっそり直してしまうことがありません。指摘が文字で残るので、何がどう直ったかをあとから確かめられます
・指摘を memory.md に1行ずつ残し、次からは maker がそれを読んでから作るようにしています。ただし、これで同じミスを防げるとは限りません（下で書きます）


◆ 実際に見つかったミス（FE要点まとめを作ったとき）

2026年11月18日に、Jarvis で基本情報技術者試験（FE）科目Aの要点まとめを作りました。maker が書いた下書きを checker がレビューして、次のような問題が見つかりました。

・二分探索木の定義：定義を簡単にしすぎていた。「どの節でも、左の部分木のすべての節 < その節 < 右の部分木のすべての節」と書き直し、「直接の子だけを比べるのではない」という注意を足した
・「衝突」と「シノニム」：説明が不正確だった（原因は、二分探索木と同じく、定義を簡略化しすぎたこと）。「別の値が同じ格納場所になる現象が衝突（コリジョン）」「衝突を起こしたキーどうしがシノニム」と、2つを分けて書き直した
・ハッシュ関数の3つの性質：「衝突発見困難性」の説明として、よく似た別の性質「第2原像計算困難性」の説明を書いていた。3つの性質を全部並べて、違いを書くように直した
・「確実に点が取れる」という言い過ぎ：有料の記事で、得点を約束しているように読めてしまう。「確実」「必ず」のような言葉は使わないことにした
・確認が済んでいないことの言い切り：無料部分で、まだ自分で照合していないのに「過去問の数値を使わないオリジナル」と言い切っていた。確認が済むまでは、読者に向けて言い切らないことにした


◆ 見つかったミスから分かったこと

・定義を簡単にしすぎたミス（第2章）と、似た用語を取り違えたミス（第5章）があった
・AIは、つい「確実」のように強く言い切ってしまうことがある
・memory.md に書いても、それだけでミスがなくなるわけではない。第2章のミスのあとで「定義は IPA の用語どおりに書く」と memory.md に書いたのに、そのあとの第5章で、ハッシュの性質の用語を取り違えるミスがまた起きた。このときも、見つけたのは checker だった

memory.md は「くり返しを減らすための手がかり」で、checker のチェックと組み合わせて使っています。


◆ この記事の下書きでも見つかった

この記事の下書きでも、checker が「記録と違う文」を見つけています。たとえば、自動実行は1回しか試していないのに「止まった2回」と書いていたところや、筆者がまだ読んでいないのに「確認・加筆した」と書いていたところです。どちらも、ログや memory.md と照らし合わせて直しました。

チェックをお願いするときは、見てほしい点を具体的に書くと、指摘が具体的になります。筆者がメモしている頼み方はこれです。

見る点：用語・数値・計算の誤り／例題の答えが正しいか／過去問や教科書の丸写しに見える部分がないか。

checker もAIなので、すべてのミスを見つけられるわけではありません。今回のFE要点まとめも、最後に自分で読み直して、自分の言葉に書き直す作業が残っています。
「AIがチェックしたから大丈夫」ではなく、「自分が読む前に、見つけられるミスを減らしておくためのもの」として使っています。

◆ その1：最初の自動実行で、ボードを書き換えられなかった

このときのログの1行目には、次のメッセージが出ていました。

▽ ここから：ログの1行目（実物。フォルダの場所を /path/to/jarvis に、設定ファイルの場所 /root/.claude.json を ~/.claude.json に書きかえています）

意味は、「このフォルダはまだ信頼されていないので、settings.json の allow（許可）を11個とも無視します。一度対話モードで Claude Code を起動して、信頼ダイアログを承認してください」です。

原因

・Jarvis のフォルダでターミナルを開き、claude を対話モードで起動する
・「このフォルダを信頼するか」を聞かれたら、承認する
・新しいPCで使うときや、フォルダを別の場所に移したときも、最初に1回これをやる

ログには、設定ファイル（~/.claude.json）を直接書き換える方法も書かれていますが、筆者のメモ（README）には、対話モードで承認する方法を書いています。

・CLAUDE.md の「進め方」に、日付のルールと「要件が足りないタスクは確認待ちにして、1回でまとめて聞く」を足した
・/interview にも「締切は必ず日付で確認する」「要件をメモ列に入れる」を足した

6. 定期実行の設定（cron）

cron（クーロン）は、Mac や Linux で「決まった時間に、決まったコマンドを動かす」ためのしくみです。これを使って、Jarvis を自動で起動できるように作っています。

執筆時点では、筆者が cron に登録して動かした記録は、まだありません。ここに載せるのは、動くように作ってある run.sh と、筆者のメモ（README）に書いている cron の設定例です。


◆ run.sh（定期実行用のスクリプト）

scripts/ フォルダに置きます。これは筆者が最初に作った版です（今の筆者のファイルには、このあと別の用途のモードと、決まった手順で GitHub に送る部分を足していますが、ここでは基本の形だけを載せます）。

▽ ここからコピー：scripts/run.sh（最初の版）
#!/usr/bin/env bash
# 定期実行用ラッパー。cron / タスクスケジューラから呼ぶ。
# 使い方: scripts/run.sh morning | hourly
set -euo pipefail
cd "$(dirname "$0")/.."
mkdir -p logs

case "${1:-hourly}" in
  morning)
    PROMPT="朝の確認：memory.md と board.md を読み、今日の優先タスクを3つまで進め、判断が必要なものと締切が危ないものだけ報告して" ;;
  hourly)
    PROMPT="board.md をチェックし、進められるタスクを1つ実行。成果物は checker でレビュー。報告は判断が必要な場合と締切超過の場合のみ" ;;
  *)
    PROMPT="$1" ;;
esac

claude -p "$PROMPT" >> "logs/$(date +%Y-%m-%d).log" 2>&1
△ ここまで

ポイント
・cd "$(dirname "$0")/.." で、スクリプトの1つ上のフォルダ（Jarvis のフォルダ）に移動してから claude を動かします。Jarvis のフォルダで動かさないと、CLAUDE.md や settings.json が読まれません
・claude -p "頼みごと" は、画面を開かずに、1回だけ頼みごとをして終わるモードです。自動実行ではこれを使います
・結果は logs/日付.log に、どんどん追記されます
・morning（朝の確認）と hourly（1時間ごと）の2つの頼み方を用意しています。それ以外の文字を渡すと、その文字をそのまま頼みごととして使います（例：Jarvis のフォルダの中で scripts/run.sh "board.md の締切を一覧にして"）

まず、Jarvis のフォルダの中で、スクリプトを実行できるようにします（最初に1回だけ）。

▽ ここからコピー：実行できるようにする
chmod +x scripts/run.sh
△ ここまで

cron に登録する前に、Jarvis のフォルダの中で、まず手で動かしてログを確認します。

▽ ここからコピー：手で試す
scripts/run.sh morning
cat logs/$(date +%Y-%m-%d).log

◆ cron に登録する

ターミナルで crontab -e と打つと、cron の設定を書く画面が開きます。そこに次の1行を足します。

▽ ここからコピー：cron の設定（1日1回）
50 8 * * 1-5 /path/to/jarvis/scripts/run.sh morning
△ ここまで

/path/to/jarvis の部分は、自分の Jarvis フォルダの場所に書き換えます。フォルダの中で pwd と打つと、場所がわかります。

読み方：左から「分・時・日・月・曜日」の順です。
・50 8 * * 1-5 → 月曜〜金曜の 8時50分 に動かす
・「*」は「毎回」という意味
・曜日は、0（または7）が日曜、1が月曜 … 5が金曜

慣れてきたら、1時間ごとに動かす設定も足せます。

▽ ここからコピー：cron の設定（1時間ごと）
0 * * * 1-5 /path/to/jarvis/scripts/run.sh hourly
△ ここまで

・0 * * * 1-5 → 月曜〜金曜の、毎時0分に動かす
・夜中に動かす必要がなければ、時の欄を「9-21」のように範囲にすると、回数を減らせます（例：0 9-21 * * 1-5）

筆者のメモ（README）にも「まずは1日1回から」と書いています。動かす回数が多いほど、プランの使える量を使います（7章）。
登録できたかどうかは、crontab -l で確認できます。


◆ うまく動かないときに見るところ

・まず logs/ フォルダのログを読みます。止まった理由が書いてあることが多いです
・「Ignoring … permissions.allow entries」と出ていたら、信頼ダイアログの問題です（5章）
・cron から動かすと、ふだんのターミナルとちがって、コマンドを探す場所（PATH）が少なくなります。ログに「claude: command not found」のように出ていたら、run.sh の中の claude を、which claude で調べたフルパスに書き換えるか、crontab の先頭で PATH を設定します（これは cron でよくある原因の1つです）
・PC がスリープしていると動きません（7章）
・Mac では、cron からファイルを読み書きするために、「フルディスクアクセス」などの許可が必要になる場合があります。筆者は Mac では試していないので、うまく動かないときは調べてみてください
・Windows には cron がないので、タスクスケジューラで claude -p を登録する方法があります。この記事では cron の例だけを載せています


◆ おまけ：note の原稿を分けるスクリプト

筆者は、Jarvis に作らせた note の原稿を、1つのテキストファイル（設定欄・無料部分・有料部分が全部入ったもの）にまとめています。それを「タイトル」「設定」「無料部分」「有料部分」のファイルに分けるのが、このスクリプトです。note に貼るときに、どこからが有料部分かがはっきりします。

原稿のテキストファイルは、次の形にしておきます。
・先頭の設定欄に「タイトル：」と「ハッシュタグ：」で始まる行を置く
・本文の前後を、「本文ここから」「本文ここまで」と書いた行と、その上下の「======」の区切り線ではさむ
・無料部分の終わりに、「▼▼▼ ここに有料ライン」で始まる行を1行だけ置く

▽ ここからコピー：scripts/make_release.py（今の実物そのまま）
"""note 用の完成原稿（note-post.txt）を、Muse がそのまま使える「公開キット」に分ける。

使い方: python3 scripts/make_release.py outputs/fe/note-post.txt outputs/fe/images outputs/release/fe-vol1
"""
import shutil
import sys
from pathlib import Path

PAID_MARK = "▼▼▼ ここに有料ライン"
BODY_START = "本文ここから"
BODY_END = "本文ここまで"


def main(src: str, img_dir: str, out: str) -> None:
    text = Path(src).read_text(encoding="utf-8")
    lines = text.splitlines()

    title = next(l.split("：", 1)[1] for l in lines if l.startswith("タイトル："))
    tags = next(l.split("：", 1)[1] for l in lines if l.startswith("ハッシュタグ："))

    start = next(i for i, l in enumerate(lines) if l.strip() == BODY_START) + 2  # 区切り線の次
    end = next(i for i, l in enumerate(lines) if l.strip() == BODY_END) - 1      # 区切り線の手前
    paid = next(i for i, l in enumerate(lines) if l.startswith(PAID_MARK))

    free_body = "\n".join(lines[start:paid]).strip() + "\n"
    paid_body = "\n".join(lines[paid + 1:end]).strip() + "\n"
    first_paid_heading = next(l for l in lines[paid + 1:end] if l.strip())

    out_dir = Path(out)
    (out_dir / "images").mkdir(parents=True, exist_ok=True)
    (out_dir / "01-title.txt").write_text(title + "\n", encoding="utf-8")
    (out_dir / "02-settings.txt").write_text(
        "価格：500円（販売設定で「有料」）\n"
        f"有料エリアの開始位置：「{first_paid_heading}」の直前\n"
        f"ハッシュタグ：{tags}\n"
        "見出し画像：images/00-cover.png\n",
        encoding="utf-8",
    )
    (out_dir / "03-free.txt").write_text(free_body, encoding="utf-8")
    (out_dir / "04-paid.txt").write_text(paid_body, encoding="utf-8")

    for png in sorted(Path(img_dir).glob("0[0-7]-*.png")):
        shutil.copy2(png, out_dir / "images" / png.name)

    n_markers = paid_body.count("【画像】")
    print(f"title: {title}")
    print(f"free: {len(free_body)} chars, paid: {len(paid_body)} chars, image markers: {n_markers}")
    print(f"paid starts at: {first_paid_heading}")


if __name__ == "__main__":
    main(*sys.argv[1:4])
△ ここまで

ポイント
・Jarvis のフォルダの中で、ファイルの先頭の「使い方:」の行のように実行します（原稿のファイル、画像のフォルダ、できたファイルを置くフォルダ、の順に指定します）。Python 3 が必要です
・説明の文に出てくる「Muse」は、筆者が note への公開をまかせている別のAIエージェントの呼び名です。Jarvis 自身は公開せず、Muse が筆者の OK をもらってから「投稿する」を押す決まりにしています（1章）。自分の使い方に合わせて書き換えてかまいません
・「価格：500円」の行は、自分の記事の値段に書き換えてください
・画像は、ファイル名が 00- 〜 07- で始まる PNG だけをコピーします


7. 料金と注意点

料金やサービスの決まりは、よく変わります。ここに書くのは執筆時点の情報と、筆者の理解です。契約や設定の前に、公式のページで最新の情報を確認してください。


◆ 料金

・Claude Code を使うには、Claude の有料プラン（執筆時点では Pro 以上）か、API の従量課金が必要です。筆者は Pro プランで使っています
・料金の金額や、どのプランで何が使えるかは、変わることがあります。この記事には金額を書きません。契約する前に、公式のページで確認してください


◆ 使える量には枠がある

・執筆時点では、Pro などのプランには、5時間ごとの枠と、1週間ごとの枠があります（くわしい量は公式で確認してください）
・自動実行も、同じ枠を使います。サブエージェント（maker と checker）を動かすと、そのぶん多く使います
・1時間ごとの実行を一日中動かすと、枠を早く使い切ることがあります。まずは1日1回から始めて、ようすを見ながら増やすのが安全です


◆ PC を閉じると止まる

・cron は、自分の PC の上で動くしくみです。PC がスリープしているとき（ふたを閉じたときなど）や、電源が切れているときは動きません
・その時間に動くはずだった分が、あとで自動でやり直されるとは限りません。朝の確認がちゃんと動いたかどうかは、ログで確かめます


◆ 規約上の注意

・個人向けのプランは、自分で使うためのものです。自分のログインで、ほかの人向けのサービスを動かすようなことは、規約で認められていないと理解しています。アカウントを友達と共有することも、認められていないと理解しています（どちらも筆者の理解です。利用規約の本文を確認してください）
・AIを使って作ったものを売るときは、売る場所（note など）の規約やガイドラインも確認します。筆者は、AIを使ったことを記事の中に書いています
・学校の課題の問題や答え、教科書・過去問のコピーは、成果物に入れません（CLAUDE.md の「任せないこと」にも書いています）。学校の課題でAIを使ってよいかどうかは、学校や先生のルールにしたがってください


◆ 秘密の情報をわたさない

・パスワードやAPIキーは、CLAUDE.md や board.md に書きません。AIが毎回読むファイルだからです
・.env などに書く場合も、settings.json でAIに読ませない設定にしておきます（3章）


8. おわりに

Jarvis は、次の4つの部品と、学習メモでできています。

・判断軸（CLAUDE.md）：何を大事にして、何を任せないか
・仕事ボード（board.md）：何を、いつまでにやるか
・実行チーム（maker と checker）：作る担当と、チェックする担当
・定期実行（run.sh と cron）：いつ動かすか
・学習メモ（memory.md）：失敗から学んだこと

Jarvis で大事にしているのは、AIに「全部やって」と任せるのではなく、「ここまではやってよい、ここから先は自分（または、OK をもらった別の担当）がやる」と線を引くことと、AIが止まったり間違えたりした原因を memory.md に1行ずつ残すことです。

正直に書くと、Jarvis はまだ作り始めたばかりです。自動実行を試したのは1回だけで、cron での定期実行も、まだ通して動かしていません。Jarvis で作った FE の要点まとめも、執筆時点（2026年11月18日）ではまだ販売前で、売上は0円です。
